## 中转（relay）核心逻辑落地（参考 New-API）

在 capi（Next.js 16）里实现了 OpenAI 兼容的中转站核心，逐块对齐 New-API（QuantumNous/new-api，源码拉到 /tmp/newapi-ref 参考）：

- `lib/relay/` 新模块：
  - `types.ts`：Channel / ApiKey（=New-API 的 Token）/ Ability / UsageRecord / RelayData
  - `config.ts`：RelaySettings（重试次数、重试状态码区间、自动禁用区间+关键词、各类倍率表、按次计费表）+ 环境变量覆盖；QuotaPerUnit=500000（$1）
  - `errors.ts`：RelayError（statusCode/code/retryable/upstreamStatusCode）
  - `pricing.ts`：模型倍率/补全倍率/缓存倍率/分组倍率，通配符匹配 + FormatMatchingModelName 归一化（去 @suffix、gizmo 通配），computeQuota/预扣估算
  - `store.ts`：RelayRegistry（JSON 文件 data/relay.json + 内存索引 group→model→channelIds 按优先级降序；渠道/密钥 CRUD；用量记录上限 2000；globalThis 单例防 HMR 重置；文件损坏自动备份重播种）
  - `selector.ts`：selectChannel —— New-API GetRandomSatisfiedChannel 等价实现：优先级降序分层、retry 降级到第 N 优先级、同层加权随机 + 平滑（全 0 权重→等权 100；平均权重<10→×100）；describeRouting 输出各层选中概率
  - `keys.ts`：Bearer/x-api-key/?key 取 key、sk-<key>-<channelId> 指定渠道、状态/过期/IP 白名单(CIDR)/额度/模型白名单（含通配）
  - `relay.ts`：主流程 —— 预扣费 → retry 循环选渠道 → 上游转发（模型映射、多 key 轮询/随机、paramOverride、流式注入 stream_options.include_usage）→ 流式 TransformStream 旁路解析 usage 透传 SSE → 失败按状态码区间重试 + 自动禁用(401/关键词) → 多退少补结算 + 用量记录
  - `admin.ts`：管理鉴权（CAPI_ADMIN_TOKEN；未设置时仅 dev 放行）
- 路由：/v1/chat/completions 接真实中转（无渠道时按 CAPI_RELAY_MOCK_FALLBACK=1 回落 mock 保文档站演示）；/v1/models 按密钥分组+白名单出路由表模型（无渠道回落目录）；/v1/me/balance、/v1/me/usage 接真实额度/用量（空时回落 demo 数据）；新增 /api/admin/{channels,keys,abilities,overview}（含 [id] 的 GET/PATCH/DELETE）
- `.gitignore` 加了 /data/relay.json（含上游 key）
