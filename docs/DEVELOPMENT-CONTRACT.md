# CAPI 开发统一契约

本文件是 CAPI 开发协作的入口规则，用来减少改版后需求、页面、接口和文档互相漂移。

## 1. 权威顺序

同一事实只允许有一个权威来源。其他地方只能引用它，不能复制一份可独立修改的定义。

| 事实 | 权威来源 | 其他位置的职责 |
| --- | --- | --- |
| 当前产品范围和行为 | 实际代码路径、服务端校验和公开文档 | 需求记录只描述本次变更，不维护独立进度状态 |
| 团队空间、计费、权限等业务规则 | 数据模型、服务端校验和已验证行为 | 复杂规则写入对应模块注释或公开文档，不维护长期计划副本 |
| HTTP API 请求/响应字段和示例 | `lib/api-spec.ts` + 实际 `app/api/**` | `content/docs` 只写使用说明，字段不得另造一套 |
| 文档导航和公开文档 slug | `lib/docs-nav.ts` | 新增文档必须同时注册导航并验证链接 |
| 模型 ID、能力、价格元数据 | `lib/models-data.ts`、`lib/models-i18n.ts` | 页面和文案从数据读取，不在组件写死 |
| 数据表结构和初始化定义 | `lib/relay/store.ts` 及相关 store | 上线前直接改定义；上线后按迁移流程处理 |
| 页面交互和权限行为 | 对应 `app/**` 路由、组件及服务端校验 | 计划文档记录目标，不能当成已实现证据 |

冲突处理顺序：实际安全约束和服务端行为 > 数据模型 > 业务规则文档 > 页面文案 > 示例文档。发现冲突时必须在同一个变更中修正权威来源和受影响引用，不能只改展示文字。

## 2. 一项变更的最小记录

每次改版、接口调整或数据结构调整都必须留下一个短变更记录（写在 PR 描述或提交信息中）：

```text
目标：用户能完成什么操作
范围：页面 / API / 数据表 / 文档
权威来源：本次修改的唯一事实来源
不变项：明确不改的兼容边界
验收：成功、失败、刷新、权限和双语场景
状态：未开始 / 开发中 / 已验证 / 阻塞
```

“已实现”只有在真实代码路径和对应验收都通过后才能使用。入队、Mock、静态检查、路由存在或 HTTP 200 都不能单独算完成。

## 3. 推荐变更顺序

1. 先改范围和业务规则，再改数据结构或服务端契约。
2. 从服务端校验、持久化和权限开始实现。
3. 页面只消费服务端返回的数据和共享类型，不复制业务常量。
4. 更新 `lib/api-spec.ts`、`content/docs` 和导航；示例必须能对应真实路径。
5. 按验证步骤跑成功与失败路径；完成后以代码和验证结果为准，不维护计划状态。

如果需求只改变文案，也要确认没有改变 API 名称、数据库字段、URL slug 或权限含义。

## 4. 提交前检查

- `rg` 检查旧名称、旧 URL、旧字段和旧产品范围是否仍出现在代码、导航、文档中。
- API 文档的 method、path、参数、状态码与 `app/api/**` 实现一致。
- 页面显示的模型、价格、统计和权限来自真实数据或明确空态，不使用未标注的占位值。
- 新增或删除路由时同步更新导航、链接和发布验证记录。
- 数据库变化遵守 `AGENTS.md`：当前未上线阶段直接修改 SQLite 定义，不添加迁移兼容层。
- `bun run lint` 和相关测试通过；不能运行时记录原因和未覆盖范围。
- 每次修改都创建一个本地 Git commit；提交前确认只包含本次任务文件。

## 5. 文档目录约定

- `README.md`：项目入口、启动方式、环境要求、统一契约链接。
- `docs/`：内部架构、决策、开发和验收约定。
- `content/docs/`：面向 CAPI 使用者的公开文档。
- 不保留根目录计划文档；进度和状态通过代码、提交、测试和发布记录判断。

当两个文档需要重复同一内容时，保留一份完整定义，另一份只写链接、适用范围和差异，避免复制整段规则。
